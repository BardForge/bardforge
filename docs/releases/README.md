# Ручной выпуск

Workflow `Manual stable Windows release` подготовлен в `dev`. Полная публикация через него ещё не проверялась: релизов пока нет. Он запускается только вручную владельцем **ShinozakiAichi** с ветки `main`, после отдельного одобрения environment `release`.

## Перед первым выпуском

1. Подготовить `release/X.Y.Z` от `dev`: стабильную версию в package.json и lockfile, датированный раздел `## [X.Y.Z] - YYYY-MM-DD` в CHANGELOG.md и содержательные заметки `docs/releases/X.Y.Z.md`.
2. Адаптировать проверки development-текста в desktop smoke к стабильной версии, сохранив проверку реального воспроизведения, импорта, экспорта и настроек. Текущая версия `0.1.0-dev.3` намеренно не допускается к стабильному выпуску.
3. Проверить сборку, безопасность, совместимость и документацию. Лично прослушать Windows-сборку и проверить звук у удалённого игрока в реальном Foundry. Два браузерных контекста не заменяют эту проверку. Foundry остаётся отдельным необязательным модулем; проверка интеграции входит в критерии первого Audio MVP.
4. Получить подтверждение владельца на PR `release/X.Y.Z → main`. Агент не сливает такой PR и не запускает публикацию самостоятельно.
5. Проверить environment `release`: единственный reviewer — ShinozakiAichi, отдельное одобрение после сборки; self-review разрешён для одного владельца; обход администратором выключен; только branch `main`. Секреты environment не нужны.

## Выполнение владельцем

Вручную запустить workflow на `main`, указать точную версию и полный SHA лично проверенного коммита, подтвердить оба сценария QA и приложить краткое безопасное описание результата. `qa_notes` публикуется в manifest: не включать персональные данные, секреты и приватные логи.

Workflow повторяет lint, format, unit, build/typecheck, dependency audit, проверки публичных файлов и лицензий, browser/transport tests, упаковку NSIS, запуск desktop и install/uninstall. После успеха владелец проверяет артефакт и отдельно одобряет environment.

Публикация проверяет точный artifact ID/run/attempt, SHA-256 каждого файла, provenance, историю одобрения, текущий SHA `main` и отсутствие существующего тега/релиза. Затем создаёт аннотированный тег, draft Release, загружает и сверяет assets через GitHub API, после чего снимает draft.

Разрешены только установщик EXE, `latest.yml`, `SHA256SUMS.txt`, `RELEASE_NOTES.md` и `release-manifest.json`. Никакие пользовательские аудио, модели, служебные документы и логи не входят в артефакт. Подпись Authenticode пока не настроена.

## Ограничения и восстановление

- Это подготовленная автоматизация, не доказательство готовности первого релиза или обновления между опубликованными версиями.
- Имена владельца и репозитория зафиксированы. При переносе проекта нужно отдельным PR обновить workflow/helpers, конфигурацию обновлений и проверить environment/rulesets.
- Push, тег или обычный PR не запускают выпуск. Весь workflow имеет read-only permissions; только job публикации после одобрения получает `contents: write` и `actions: read`.
- При ошибке проверки или API публикация прекращается. Если ошибка случилась после создания тега, тег и draft остаются для проверки владельцем; автоматического удаления/перезаписи нет.
- Если `main` изменился после QA или во время публикации, выпуск останавливается. Для повторного запуска нужен **Re-run all jobs**, чтобы artifact соответствовал run attempt.
- Локальные проверки валидации не заменяют реальное одобрение environment, загрузку assets и тестирование выпущенного обновления. Эти проверки выполняются при первом отдельно разрешённом выпуске.
